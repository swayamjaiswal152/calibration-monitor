# System Architecture: Forecast Calibration Monitor (v2)

This document outlines the distributed, stateless architecture designed for real-time forecast calibration monitoring at scale.

## 1. High-Level Architecture Diagram

The system has been heavily refactored to support horizontal scaling across multiple Kubernetes pods or Docker containers, ensuring zero single-points-of-failure (SPOFs) and highly efficient background processing.

## 2. Component Breakdown

| Component | Technology | Responsibility |
|---|---|---|
| **API Service** | FastAPI, `asyncpg`, Uvicorn | Exposes REST endpoints and WebSocket connections. Completely stateless to allow horizontal scaling. |
| **Realtime Pub/Sub** | Redis | Replaces the legacy in-memory WebSocket manager. Allows any API pod to broadcast metric updates across all connected clients regardless of which pod they are connected to. |
| **Data Persistence** | PostgreSQL (TimescaleDB) | Stores `forecasts`, `actuals`, `alerts`, and `conformal_state`. Utilizes connection pooling and async drivers. |
| **Drift Worker Engine** | Python, SQLAlchemy `text()` | A continuously running background process (scaled separately) that computes rolling window metrics natively in SQL (replacing heavy Pandas computations) every 15s. |
| **Conformal Engine** | Python | Implements Adaptive Conformal Prediction logic: `q_{t+1} = q_t + eta*(err - alpha)` auto-widening intervals upon detected drift. |
| **Frontend** | React, Vite, Recharts | Provides live visualization of rolling coverage, What-If simulation slides, and Conformal adjustment controls. |

## 3. Communication Patterns

### Data Ingestion (REST)
1. The client (or Locust load tester) sends `POST /forecasts` to record `t+1` predictions.
2. The client sends `POST /actuals` when ground truth data arrives.
3. The API layer (`asyncpg`) directly commits these to the PostgreSQL instance. No background tasks are initiated on ingestion to maintain high throughput.

### Metric Evaluation (Distributed Worker)
1. The `app.worker` containers compete for a **distributed Redis Lock** (`drift_job_lock`) to ensure only **one** worker processes metrics at a time (preventing race conditions and DB hammering).
2. The active worker utilizes native PostgreSQL aggregation `AVG(CASE WHEN ...)` to calculate PICP, MPIW, and MAE across a 168-hour rolling window.
3. If the PICP (Coverage) drops below the 90% target limit, an alert is triggered.

### Realtime Client Updates (Redis Pub/Sub -> WebSocket)
1. Upon completing a metric calculation cycle, the active Worker publishes the JSON results to the Redis `metrics_channel`.
2. Every FastAPI pod maintains an active async subscription to the `metrics_channel`.
3. When a FastAPI pod receives a message from Redis, it instantly iterates through its locally connected WebSockets and pushes the data to the client frontend.

## 4. Key Performance Improvements (over v1)

- **Stateless API:** By moving the APScheduler out of `main.py` and into a dedicated `worker.py`, the FastAPI pods are now completely stateless and can be scaled infinitely without duplicating background jobs.
- **Optimized Compute:** Removed the heavy Pandas DataFrame operations (`df.mean()`, `.abs()`). Metrics are now computed entirely inside PostgreSQL using native optimized aggregation logic.
- **WebSocket Scalability:** The Redis Pub/Sub integration means a client connected to `API Pod A` will still receive live updates generated by the background worker, solving the cross-pod communication barrier.
